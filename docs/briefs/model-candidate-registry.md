### Дополнительные локальные следы, не готовые реестры

- `sources/property/devdb/README.md` и [`manifest.json`](../../sources/property/devdb/manifest.json) описывают локальную PostgreSQL 17.11/PostGIS 3.6.0 и smoke/integration harness. `data/property/devdb/` отсутствует. Манифест говорит, что regular `novostroy` service не seeded; 3 разобранные XML offers и adversarial rows находились в изолированной `property_test_*` схеме, источник явно synthetic. Это инфраструктура/проверка, не real project inventory, и её строки нельзя считать объектами рынка.
- [`yandex_tsv_sample.json`](../../data/property/yandex_tsv_sample.json) хранит только metadata запроса 4 KiB/22,259,466-byte `newbuildings.tsv`; временная raw sample удалена. В 13 просмотренных строках предполагаются region/project ID/label, queue, handover, address, building ID и URL, но headerless schema inferred. Полной локальной выгрузки нет; redistribution/public-display rights `unknown`, поэтому это не публикуемый список и не разрешённый dedup source.
- Документы [`property.md`](property.md) описывают ЕИСЖС, YRL и bnMAP как потенциальные каналы; в перечисленных локальных реестрах нет полученной ЕИСЖС project dump, лицензированного live offer feed или реальных unit-price rows. bnMAP требует отдельный entitlement; Yandex TSV — справочные метки, не offers.

## Как сопоставлять и не задвоить

1. На уровне источника сохранять `source_id + source_record_id` и исходный namespace. EstateLine надёжно дедуплицируется только по linked page ID после выбора latest record across categories; EstateLine row ID не использовать как project identity. Текущий output уже выбирал latest **до** фильтра и оставляет conflicts/review отдельно.
2. OSM dedupe — сначала `(osm_type, osm_id, osm_version)` как одна source object; это не уникальность корпуса: relation/ways, соседние секции, старые footprints и общий стилобат требуют отдельной проверки членства/контуров. Нельзя сливать EstateLine/OSM по одному названию или адресу без strict key и проверки корпуса.
3. Minstroy — отдельные permit events. `permit_number`, serial, EGRUL и текст объекта помогают искать документы, но не являются подтверждённой связью с тем же building ID. 27 Sochi rows не добавляют московских ЖК. Yandex `project_id/building_id` были только в невосстановленном sample; даже при будущем доступе нужны отдельные права и точный crosswalk.
4. Полезные поля для карты: EstateLine даёт координатную **точку** только 10 записям, не границы дома; OSM даёт 756 polygon footprints, но не проектную идентичность; Minstroy не даёт координат. Floors/handover и status всегда оставлять dated source assertions. Ни один источник не даёт квартиру, цену или наличие лота.

| Запись | Минимальные видимые поля | Что пример не доказывает |
| --- | --- | --- |
| `estateline:10653` | `apartment_complex`, 6 floors, latest-known `2024-12-22`, точка `verified` | Не текущая стадия, не footprint и не лицензия EstateLine на публикацию. |
| OSM `relation:17582829` | polygon candidate; есть `building:levels:underground`, точного above-ground `building:levels` нет | Не число надземных этажей, не ЖК ID и не подтверждение актуальной стройки. |
| Minstroy row (permit event) | dataset release `2026-05-29`; event/permit date — отдельный источник-факт | Не московский проект (в residential subset — Sochi), не уникальный проект и не live construction status. |

**Вывод для счётчика максимума:** 1,473 — это не единственный локальный список, но и не «все московские новостройки». Есть 756 пространственных OSM candidates и дополнительные 59 Estateline review records; Minstroy московской жилой строки не даёт, а devdb — synthetic tests. Их нельзя суммировать как уникальные комплексы. Корректный восстановитель должен выдавать per-source candidates, source-backed identity links и отдельные причины review/rejection; неизвестные связи и пустая геометрия остаются явными.
