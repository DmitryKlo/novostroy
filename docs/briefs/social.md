# Social infrastructure data brief: Moscow

## Decision

Use OpenStreetMap (OSM) as the first reproducible source for a small POI pilot and, if coverage and ODbL obligations fit the product, as a city-scale source from an owned regional extract. For production-scale collection, prefer a pinned OSM dump over repeated public Overpass requests. Keep an import/source manifest and preserve attribution and license metadata. OSM data is licensed under ODbL; maps and exported data need the required attribution and license notice ([OSM copyright and license](https://www.openstreetmap.org/copyright)). Public Overpass servers are shared infrastructure, with explicit runtime and memory limits and load shedding; use them for small, bounded lookups, not bulk Moscow extraction ([Overpass commons and quotas](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)).

The Moscow Open Data portal is a candidate for official facilities and district-level datasets, but access and dataset suitability are not yet established. The developer documentation URL returned HTTP 403 during this review ([portal documentation](https://data.mos.ru/developers/documentation)). A prior probe reported an API-key 401 and candidate dataset IDs 503, 505, and 747; treat those IDs and their schemas, freshness, geometry, completeness, and reuse terms as unverified until each endpoint is fetched and validated. Do not build a pipeline against guessed IDs or scrape the portal UI.

2GIS can be considered only after checking current product-specific terms and receiving the rights needed for the intended use. Its published API legal terms restrict storage, caching, processing, and database creation of returned content; access to an API or a display key does not grant permission to build a persistent POI corpus ([2GIS API legal information](https://law.2gis.ru/api-rules)). Keep 2GIS behind a disabled adapter until rights for storage, derived rankings, redistribution, and commercial use are confirmed in writing.

## Spatial and semantic rules

- Bind each district polygon to an authoritative source, boundary version, effective date, and district identifier. Moscow's municipal formations changed in 2024; keep them distinct from city districts and pin the exact geometry set used by the product ([Moscow Law No. 13 of 8 May 2024](https://www.mos.ru/upload/documents/docs/343/Zakon13-ajbn2.pdf)). Never assign a district from a stale name-only lookup. Record the boundary set used by every result.
- A POI's mapped point, a residential building centroid, and a usable entrance are different things. Prefer a surveyed/mapped public entrance and route to that entrance. If no entrance is available, use a clearly recorded access point or straight-line estimate and set `approximate=true`; do not silently route to a footprint centroid.
- OSM tags such as `amenity=clinic` or `amenity=hospital` establish a mapped category, not ownership, operating status, service quality, or eligibility for a user's needs. Keep those fields unknown unless a suitable authoritative source supplies them. Do not infer public/private ownership or quality from names, tags, ratings, or proximity.
- Use a versioned, auditable v1 index on the backend's **0–1 scale**: for the user's selected categories, use equal weights unless they supplied explicit weights, and set a configurable walking threshold `T` (default proposal: 15 minutes). For each category `c`, find the shortest pedestrian-network time `t_c` from a known residential public entrance to a known public POI entrance. If source and routing coverage are complete, score `s_c = max(0, 1 - t_c / T)`; a verified absence within the fully covered area has score 0. Publish each `t_c`, `s_c`, source snapshot, and method version. Define `coverage = total weight of requested categories with validated POI and route coverage / total requested category weight`. If coverage is unknown or below 1.0, keep the aggregate index null and show the coverage ratio; do not treat missing categories as zero or renormalize around them. The original 50-feature Overpass payloads carry `coverage=sample`; city-scope OSM extracts have mapped-feature completeness unknown. Neither a sample nor an extract alone produces a neighborhood score.
- A nearest-POI overlay may report great-circle `straight_line_m` with `metric=straight_line`, OSM identity, and explicit `from_access_kind`/`to_access_kind`; it must not imply pedestrian route length or time. The current sample payload keeps `index=null`, `coverage.status=unknown`, and source coverage `sample`.
- Route from public access points. If an entrance is missing, only use a documented source access point as an estimate and set `approximate=true`; do not route to a building-footprint centroid. An approximate result must retain that flag in the response. If there is no usable access point or route graph, travel time and the category score stay unknown.
- Recommendations apply hard budget and district constraints before ranking. If the requested constraints are ambiguous or no verified offer satisfies them, ask a targeted clarification or return no match. Never relax a budget/district filter silently, invent offers, or imply that an infrastructure score predicts medical/education quality. No ML-generated social labels are permitted.

## Pilot and provenance

The initial pilot uses two small, documented Overpass queries inside one compact central-Moscow bounding box: a pharmacy sample and one multi-category sample. Keep exact queries, endpoint, retrieval timestamp, HTTP status, bbox, returned OSM IDs/versions/timestamps, byte count, SHA-256, and normalizer version in separate manifests. Include attribution (`© OpenStreetMap contributors`) and the ODbL link in any data distribution. Keep raw response and normalized records separate. A later city refresh should use a pinned regional extract and exact local boundary clipping, not tiled public Overpass scraping.

The Python classification adapter should preserve original OSM tags and source identity, emit a stable normalized category plus a reason/rule version, and leave uncertain or conflicting features `unclassified` for review. It must not synthesize coordinates, rating, ownership, quality, operating status, or district membership.

## Open checks

Validate portal dataset IDs and terms, obtain and version authoritative post-2024 district polygons, establish the route graph and entrance source, and measure category-level coverage before publishing an index. Record separate provenance for buildings, POIs, boundaries, routing, and offers. Citywide completeness and quality remain unproven until those checks are complete.

## New buyer-facing criteria and route-source gate

The machine-readable field registry is [`docs/criteria/social.json`](../criteria/social.json). It uses stable keys and the shared `facts[key]` contract. Walking time is seconds from a residential public entrance to a facility/stop entrance or waiting point, and is produced only by a pedestrian router. Straight-line Haversine measurements remain separate fields in meters. An OSM node is not automatically a public entrance; centers and other approximate points keep explicit access flags.

For transit, keep three distinct facts: walking time to a mapped metro entrance, the station name joined from an explicit station/entrance relationship, and an actual public-transport itinerary from the complex to a metro entrance. The bus/tram result is populated only when a router returns a direct route with a bus or tram leg and zero transfers. Nearby stops do not prove that route exists. OSM's [`railway=subway_entrance` documentation](https://wiki.openstreetmap.org/wiki/Tag:railway%3Dsubway_entrance) distinguishes a station entrance from the station itself and says the station relationship is separate; the original 50-feature Overpass pilot did not include metro coverage. The later city extract contains mapped entrances but does not establish a complete station or transit graph.

The route-provider review found two technically relevant products. [Yandex Router API](https://yandex.com/maps-api/products/router-api) documents walking and public-transit routing in Russia, but requires a key and paid product plan; storage rights depend on the chosen license. [2GIS Routing API](https://docs.2gis.com/api/navigation/routing/overview) documents walking, metro, bus and tram routes and direct-route options, but its [published API rules](https://law.2gis.ru/api-rules) prohibit saving/processing returned data outside a narrow geocoder cache exception. Therefore neither is enabled for persistent citywide enrichment until product-specific terms and storage/derived-data rights are approved. No external route endpoint is configured and no paid route calls have been made. The local Valhalla adapter is explicit opt-in and pedestrian-only; it cannot supply transit facts.

Clinic descriptors are separate, nullable evidence: ownership (`public`/`private`), participation in the Moscow OMS program, published paid services, and DMS insurer/product networks. The [2026 Moscow territorial program, Appendix 3](https://dgp69.mos.ru/public/docs/legaldoc/ppm-30-12-2025-3389-pp.pdf?1768375555=) lists organizations and separately marks city-budget assignment and OMS participation. OMS participation does not mean every service is free. DMS must be tied to an insurer, named product/plan, covered service and effective date; it is not inferred from ownership or OMS status. No single citywide public DMS network source was verified, so the field remains unknown until an official insurer directory or authorized feed is available.

The original 50-feature OSM POI pilot remains a real, bounded sample (`coverage=sample`, completeness unknown); its query did not request transit or emergency facilities. A later city-extract POI table contains 50,330 category records, including mapped bus/tram stops, metro entrances, police, ambulance, and fire facilities. These are observed OSM records, not a complete inventory; missing features in either source do not prove absence. The criteria taxonomy preserves the original normalized sample and classifies city-extract tags separately. Batch enrichment is bounded, accepts explicitly supplied routers, defaults to zero route requests, and keeps the accessibility index null until required source and route coverage are complete. See [`sources/social/taxonomy.py`](../../sources/social/taxonomy.py), [`sources/social/enrichment.py`](../../sources/social/enrichment.py), and [`sources/social/accessibility.py`](../../sources/social/accessibility.py).

## Citywide OSM extract and routing feasibility check

The 2026-10-08 [Geofabrik Central Federal District extract](https://download.geofabrik.de/russia/central-fed-district-261008.osm.pbf) was downloaded once after approval (880,118,821 bytes, SHA-256 `73e08b34988ec5780b5fd2d94a748b41f019a9d19ebbd385bede4e3ba7bb0d16`). The local extract [`data/social/osm_moscow_city_261008.osm.pbf`](../../data/social/osm_moscow_city_261008.manifest.json) is 79,913,674 bytes and pins OSM replication timestamp `2026-10-08T20:21:06Z`; it was cut against relation 102269 v422. The extract uses Osmium `complete_ways`, so source ways can extend beyond the polygon. Every derivative below is intersected with the exact pinned polygon. This OSM boundary is community-mapped geometry, not legal-boundary certification.

The clipped [`roads GeoParquet`](../../data/social/osm_moscow_roads_261008.manifest.json) has 463,288 highway-way geometries. It preserves OSM way IDs, class, raw tags and fields relevant to later pedestrian-graph work (`foot`, `access`, `oneway`, `bridge`, `tunnel`, `level`, and `layer`). Many rows are footways and service ways; they are OSM ways, not proof of public access. This file is map geometry only, not a routable pedestrian graph, route result, or travel-time estimate.

The clipped [`social POI GeoParquet`](../../data/social/osm_moscow_social_pois_261008.manifest.json) has 50,330 category records across the 13 social taxonomy keys, including multiple categories for a shared OSM feature when its tags support them. It preserves OSM type/ID/version/timestamp and raw tags. Polygon and line features retain source geometry; the builder does not make centroids. A point is an entrance only when source tags identify an entrance; bus/tram nodes are recorded as mapped waiting points. Counts describe this OSM snapshot, not total real-world facilities or completeness.

The surfaces export keeps separate polygon/line layers: 1,556 park/garden polygons, 3,860 water polygons, and 5,857 waterway lines. Osmium assembles closed ways and multipolygon relations before clipping; the verified GeoParquet retains 65 park interior rings and 256 water interior rings, including island holes. See the [`surfaces v2 manifest`](../../data/social/osm_moscow_surfaces_261008_v2.manifest.json). The first surfaces attempt produced empty park/water files because generated area IDs were mistaken for source IDs; those files and their manifest remain on disk but are invalid/superseded. Use only the `_v2` files referenced in the v2 manifest.

The isolated tool environment is `.runtime/geodata-env`; its package recipe is [`sources/social/geodata-environment.yml`](../../sources/social/geodata-environment.yml). `sources/social/build_citywide_roads.py`, `build_citywide_surfaces.py`, and `build_citywide_pois.py` rerun bounded local processing against the pinned source and boundary. They refuse to overwrite outputs. Source extract, relation, derivatives and hashes are listed in their manifests; OSM data remains subject to ODbL attribution and share-alike terms.

An official Linux x86_64 [`pyvalhalla` 3.9.0 wheel](https://pypi.org/project/pyvalhalla/3.9.0/) is installed only in the project-local `.runtime/geodata-env` (37,536,056 bytes; SHA-256 `6d027f88f8e0d8055d1a4df8c45e6d78bfdaf319d4ce69f7eecd3940b77dc6b3`). The wheel provides both the Python `Actor` bindings and native `valhalla_build_tiles`; the [official builder guide](https://valhalla.github.io/valhalla/mjolnir/getting_started_guide/) describes the graph-generation pipeline. A pedestrian-only graph was built offline from the already-pinned Moscow OSM extract, without another geodata download: 24 graph tiles / 166,385,392 bytes, 21.2 seconds, two builder threads under a 6 GiB memory and 200% CPU cap. Config, source/build metadata, per-tile hashes, and validation are in [`build_manifest.json`](../../data/social/valhalla_moscow/build_manifest.json); the pinned config is [`valhalla_pedestrian.json`](../../data/social/valhalla_moscow/valhalla_pedestrian.json).

Seven offline route checks between real OSM POIs with explicit source `access_point` geometry succeeded: bus/tram waiting points to mapped metro entrances, a clinic, pharmacy, police station, kindergarten, and supermarket. Valhalla returned 4–41 graph edges per route with OSM way IDs; source-to-route snaps were 0.006–0.115 m. The network distances were 0.151–1.166 km and the router's pedestrian estimates were 107–825 seconds. These are smoke checks on one OSM snapshot, not a completeness claim, current-closure check, or journey-time guarantee. Live closures and current facility operation are not modeled. Endpoints without `entrance_known` or `mapped_waiting_point` source access geometry are rejected; no centroid fallback is allowed. See [`route_smoke_validation.json`](../../data/social/valhalla_moscow/route_smoke_validation.json), [`route_cli_sample.json`](../../data/social/valhalla_moscow/route_cli_sample.json), and the [offline CLI](../../sources/social/valhalla_offline.py). The official [Actor API](https://valhalla.github.io/valhalla/python/actor/) supports local routing and [`trace_attributes`](https://valhalla.github.io/valhalla/api/map-matching/), used here to preserve graph-edge and OSM-way attribution.

This prototype does not yet route from residential complex entrances or establish citywide category coverage. Accessibility scores therefore remain null until the origin entrance, POI coverage, and router coverage are validated for every requested category. Straight-line distance remains a separate metric. `NOVOSTROY_VALHALLA_ENDPOINT` is still unset; transit routes remain separately gated by provider rights, and nearby stops alone never establish a direct bus or tram itinerary.
