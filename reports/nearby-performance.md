# Nearby: локальная проверка производительности

Проверка 2026-10-10 выполнялась офлайн из `.runtime/dev-env/bin/python` через `rtk proxy`, без HTTP-сервера и браузера. Код `backend/nearby.py` запускает один ленивый процесс `.runtime/geodata-env/bin/python` через `rtk`, держит его для следующих запросов и загружает локальный OSM POI snapshot и пешеходный граф. Измерения относятся к этому host и выбранной точке карты; это не метрика времени загрузки страницы или FPS.

Для источниковой точки `mappt_8b935e0da38e2bb75bc3629d` (37.48072, 55.54767) первый `nearby_for_point` занял 0.375 с, повторный идентичный запрос — 0.001 с. В каждом ответе было по пять объектов метро, образования и медицины. Отдельная проверка владельца nearby получила 14 маршрутов и один отказ по порогу привязки к графу; самый длинный возвращённый маршрут имел 317 координат. Реализация ограничивает подбор пятью объектами на категорию (не более 15 вызовов `Actor.route` на новый выбор) и выдачу геометрии 512 координатами на маршрут. Кэш ответов ограничен 128 ключами: на синтетических 130 разных ключах старейший был вытеснен, последний остался.

После загрузки графа `/proc` показал два процесса: оболочка `rtk` с `VmRSS=8596 kB` (8.4 MiB) и дочерний geodata Python с `VmRSS=383888 kB` (374.9 MiB), вместе около 383.3 MiB. Повторный запрос сохранил тот же PID оболочки; отдельного Python на каждый объект нет. Это моментный RSS одного воркера, а не верхняя граница памяти при 128 заполненных кэш-записях. Штатный `scripts/dev.py` запускает Uvicorn без опции нескольких workers; иной способ запуска потребует умножить бюджет на число API-процессов.

При пяти одновременных запросах viewport и искусственной задержке ответа 0.35 с три запроса завершились на одном PID, два быстро получили `local nearby worker queue is busy`. Так проверены предел очереди в три слота и отсутствие размножения локальных воркеров в этом сценарии. Принудительная имитация таймаута через пустой результат `select` обнулила ссылку на воркер; через 0.15 с ни оболочки, ни дочернего Python в `/proc` не было. Это проверка ветки очистки, не реального 30-секундного зависания графа. Совпадающие запросы сериализуются и после первого используют LRU; при переполнении очереди повтор также может получить busy. Отмена HTTP-запроса клиентом, задержка при быстром перемещении карты и фактическая работа на iPhone не проверялись.

Материальная ревизия основной карты city-v11 проверена отдельно в [отчёте по карте](point-map.md): она не меняет POI, дороги, геометрию зданий или этот воркер.
