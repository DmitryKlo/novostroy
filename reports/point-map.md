# Точки доступных новостроек на основной карте

Состояние кода и локальных данных на 2026-10-10. Пользователь выбрал **только подтверждённые координаты**. Новый `GET /v1/map/points` объединяет 10 строго привязанных адресных точек из 1473 принятых записей реестра и 756 точек внутри исходных OSM-полигонов строящихся жилых объектов. Остальные 1463 записи реестра остаются без маркера: приближённые адресные, районные и соседские координаты не подставляются. OSM-точка означает нанесённый контур, а не проверенное соответствие конкретному ЖК или актуальную стадию строительства.

Маршрут возвращает **766 исходных записей на 765 точных координатных позициях**. Одна пара разных источников совпадает по координатам, но её связь с одним проектом остаётся на review; обе записи имеют разные opaque `point_id` и отдельные типизированные цели. Это не 766 уникальных ЖК. Реестровый маркер ведёт к `registry_id`, OSM-маркер — к `candidate_id`. Никаких URL тайлов, контуров или высот ответ не содержит; выбор OSM-точки открывает лёгкую карточку точки, а переход на `/models` требует отдельного клика «Оценка модели». Индивидуальный 3D при выборе маркера не загружается. Перечень маркеров не ограничен 48 строками страницы списка.

Поиск применяется к названиям обеих групп. `status` и `kind` имеют данные только у реестра: при таком фильтре mapped construction исключаются, а `counts.excluded_mapped_by_registry_filters` явно показывает число исключённых подходящих по поиску OSM-записей. `counts.registry_points_total` сохраняет нефильтрованные 10 точек для отдельного счёта 1463 записей без координат; при активном фильтре интерфейс считает отсутствие координат в отфильтрованном наборе реестра. Ответ несёт ID снимков, даты и обязательную OSM-атрибуцию. Реестровые данные сохраняют статус `user_supplied_internal_use` в существующем локальном/internal режиме; новый маршрут не создаёт открытую лицензию и не служит разрешением на публичное перераспространение.

Дополнительно сохранены доступные адреса и прямые метки ЖК с отдельным основанием каждого поля: у 10 реестровых точек — собственные адреса; у 756 OSM-точек — 203 адреса (153 street+house, 6 place+house, 12 street, 32 place) и 41 явная ЖК-метка (34 `addr:place`, 6 `name`, 1 именованная родительская relation). Ещё 553 OSM-точки остаются без адреса, 715 — без метки ЖК. Только реестровые точки имеют `known_catalog_registry_id=self`; все OSM-точки оставляют его `null`, включая совпадающую с реестром пару. Источник метки нельзя выдавать за подтверждённое соответствие каталогов. Разбор исходных полей — в [адресном brief](../docs/briefs/point-map-label-data.md).

Активный city-v11 изменяет только фактор lit-материала зданий с `[0.36,0.42,0.46,1]` на `[0.40,0.46,0.50,1]` у 212 обзорных и 3396 детальных GLB. [Независимый аудит](../integration/audit_city_brightness.py) после переключения проверил все 3608 JSON-материалов, полную идентичность BIN с v10, неизменность 212 внешних региональных JSON, ссылок и приватности, а также сохранение ground-v3, roads-v2 и model-run. Это доказывает узкую материальную правку, но не измеряет экранный оттенок или FPS на устройстве.

В клиенте OSM-стройки получили отдельный более приглушённый терракотовый цвет маркера (`#a86c54` против реестрового `#c96747`). Для прежнего roads-v2 обзор использует крупные региональные ленты; точные дорожные ячейки допускаются после приближения до 1 км, сохраняются до 1,5 км при отдалении и запрашиваются только при неподвижной камере и достаточном адаптивном качестве. Tileset и кэш при смене масштаба остаются теми же. Это проверено по исходнику и pure policy; фактическая смена LOD и визуальный оттенок в браузере ещё не измерены.

Проверено в процессе без TCP: [`integration/check_map_points.py`](../integration/check_map_points.py) прошёл JSON Schema/OpenAPI, полный состав 10+756, 765 позиций, отсутствие слияния совпавшей пары, правильную типизированную цель, поиск обеих групп, исключение OSM при `status`/`kind`, 422 для неизвестного `kind`, отсутствие model asset URL и независимость от первой страницы списка. Локальный ответ использует private weak ETag/304 с revalidation. Запуск launcher gate добавлен в `scripts/dev.py`: управляемый старт или `restart-api` сверяет новый маршрут с тем же снимком реестра и активным run моделей; 17 offline-тестов launcher прошли. Backend после добавления POI: 41 фокусный тест PASS. Web: 39 unit-кейсов, включая прежние 4 map-points и 6 новых nearby, и production build PASS (финальные `index-EX85z1fY.js` / `index-qD8ozMuk.css`), включая сохранение выбора при переключении видимости карты и защиту от устаревшего ответа карточки после смены фильтра. Добавлены native DTO без включения неподдерживаемого нативного реестра: syntax check разобрал 13 C# файлов под Editor/Android/iOS без ошибок. Эти наборы могут пересекаться, поэтому общий суммарный счёт не заявляется.

Воспроизвести узкую offline-проверку из корня проекта:

```bash
rtk proxy .runtime/dev-env/bin/python integration/check_map_points.py
rtk proxy .runtime/dev-env/bin/python -m pytest integration/test_dev_startup.py -q
rtk dotnet run --project mobile/Tests/Novostroy.Source.Syntax.csproj
```

Для уже работающей управляемой пары новый backend применяется одной командой из обычного терминала того же компьютера: `rtk python scripts/dev.py restart-api`. Затем открыть основную карту и `/models?decision=rejected`. В текущей ограниченной среде host API не перезапускался; live HTTP, браузерная карта, iPhone и фактическая скорость не подтверждены. Source coverage и ограничение прав подробно зафиксированы в [`point-map-coverage.md`](../docs/briefs/point-map-coverage.md).
